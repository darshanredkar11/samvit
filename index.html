The problem

Every agent starts from zero.
Every time.

Mixed AI teams are becoming real. But each tool lives in its own silo — no shared memory, no handoffs, no coordination.

🧠
Knowledge evaporates
Darshan's Claude spent 2 hours figuring out why the auth was broken. Rahul's Antigravity will spend the same 2 hours tomorrow. There's no shared memory.
📋
Work gets duplicated
Three agents, one task, no queue. Two start the same work. One finishes. The other's changes get overwritten. Nobody knows who did what.
💬
Messages fall into voids
Rehma's Codex finishes a review at 2am. Darshan's Claude won't see it until someone manually pastes it into the next session — if at all.
☁️
Everything needs the cloud
Every workaround — shared Notion, S3 buckets, SQS queues — requires accounts, keys, and infra that none of the agents can natively read or write.
How it works

Connect any MCP-compatible AI tool in under 5 minutes. No SDK. No extra config beyond a token per agent.

🧠 Memory

One agent learns.
Every agent knows.

Vector embeddings plus a key/value store that any agent can write to and query. all-MiniLM-L6-v2 runs entirely local — no OpenAI calls, no data leaving your machine.

  • Semantic search — finds meaning, not just keywords
  • Exact key/value lookup for structured data
  • Private per-agent + shared global namespace
  • Atomic write — vector and KV in one transaction, always consistent

# Darshan stores an architecture decision remember("Stripe webhook validation uses HMAC-SHA256. Secret is STRIPE_WEBHOOK_SECRET in .env. Always verify before processing.") # Rehma — different tool, hours later recall("how do we validate Stripe webhooks?") → results: [ { score: 0.96, content: "Stripe webhook validation uses HMAC…", agent: "darshan", namespace: "global" } ] # Named keys for structured lookups remember("postgresql://prod-host/db", key="db.prod.url") recall(key="db.prod.url") → exact match, no embedding needed
📋 Tasks

Work goes to exactly
one agent. Every time.

SELECT FOR UPDATE SKIP LOCKED — the same battle-tested primitive Postgres uses for job queues — guarantees no two agents ever pick up the same task, even under thundering-herd load.

  • Priority + tag-based routing (OR filter)
  • Claim token prevents unauthorised completion
  • Auto-release after configurable timeout + 5 min grace period
  • Redpanda event on every status change for downstream listeners
tasks.py
# Sachin creates the work items tasks = [ { title: "Write auth tests", tags: ["backend"], priority: 2 }, { title: "Fix CORS on /upload", tags: ["backend"], priority: 1 }, { title: "Review PR #42", tags: ["review"], priority: 3 }, ] # Three agents claim concurrently — each gets a different task darshan → claim() → "Review PR #42" (priority 3, locked ✓) rahul → claim() → "Write auth tests" (priority 2, locked ✓) rehma → claim() → "Fix CORS" (priority 1, locked ✓) # Done — result attached done(task_id, claim_token, result={ tests: 14, passing: 14 })
💬 Messaging

Agents leave notes for
each other across sessions.

Async by design. An agent sends a message at 2am; the recipient reads it when they start their next session. Directed or broadcast. Topic-filtered. Peek without consuming.

  • Direct messages + topic-based broadcasts
  • mark_read: false to peek without consuming
  • Message reads tracked in a join table — no unbounded array growth
  • Fanned out via Redpanda for real-time subscribers
messaging.py
# Rehma finishes a review — 2am, different timezone say(to="darshan", body="PR #42 approved. One nit on line 87 — consider early return instead of nested if.") # Broadcast to all agents on a topic say(topic="ops", body="v2.1 deployed to prod. All green.") # Darshan reads next morning read() → [ { from: "rehma", body: "PR #42 approved…" }, { from: "broadcast", topic: "ops", body: "v2.1 deployed…" } ] # Peek without consuming the message read(mark_read=False) → same messages, unread state preserved

Setup

Four steps to a coordinated team.

No cloud account. No API keys. No configuration beyond a token per person.

1

Clone and start

One command brings up the MCP server, Postgres with pgvector, and Redpanda. The embedding model is baked into the Docker image — no download on first run.

2

Register each agent

One HTTP call per person. Each returns a bearer token. Handles are validated and lowercased. Tokens are bcrypt-hashed — the server never stores the raw value.

3

Add to your AI tool

Drop three lines into your MCP client config. Claude Code, Codex, any tool that speaks MCP — it's the same config block.

4

Start using it

Your AI now has remember, recall, claim, done, say, read. Ask it to use them. It will.

# 1. Start everything git clone https://github.com/darshanredkar11/samvit cd samvit docker compose up -d # Verify it's up curl http://localhost:8765/health → {"status": "ok", "service": "samvit"}
# 2. Register each person (once) curl -X POST http://localhost:8765/v1/agents/register \ -H "Content-Type: application/json" \ -d '{"handle": "darshan", "provider": "claude"}' → { "agent_id": "…", "token": "samvit_…" }
# 3. ~/.claude/settings.json { "mcpServers": { "samvit": { "type": "sse", "url": "http://localhost:8765/sse", "headers": { "Authorization": "Bearer samvit_…" } } } }
