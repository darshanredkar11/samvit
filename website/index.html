The two gaps in production AI coding

Your agents are isolated and expensive.

Most teams face two problems: agents can't coordinate across sessions, and every token they read costs money. Solving only one leaves you with a fragile or expensive pipeline.

GAP 1 — Coordination

Agents have no shared memory or task ownership.

Agent A learns your auth flow. Agent B repeats the same investigation tomorrow. Two agents claim the same issue because neither sees ownership. Humans copy notes between terminals. Samvit solves this: one MCP server for shared memory, atomic task claims (FOR UPDATE SKIP LOCKED), and durable messaging — PostgreSQL-backed, provider-agnostic.

GAP 2 — Security & Audit

Multi-team deployments need isolation and compliance.

Samvit provides workspace isolation (multi-team safe), role-based access control (admin/operator/auditor), and complete audit logging of every action. Ethical guard automatically blocks secrets/PII before storage. All mutations are logged for compliance — exactly what enterprise customers require.

For engineering teams

What the combined server delivers.

01

Shared persistent memory

Any agent on any machine can remember a decision and any other agent can recall it — by semantic similarity or exact key. No more context resets between sessions. Semantic search uses local embeddings (BAAI/bge-small-en-v1.5).

02

Collision-free task ownership

claim atomically locks a task via FOR UPDATE SKIP LOCKED. Two agents never receive the same work. renew extends leases; done records structured results. Results can be up to 1 MB.

03

Durable agent messaging

say sends directed or broadcast messages with topic routing. read consumes with mark-as-read tracking across a join table. Messages survive agent restarts and session boundaries.

04

RAG and code intelligence

ingest documents (PDF, MD, TXT) and search_docs by semantic similarity. index_code builds a graph of symbols (Python AST, JS/Go/Rust/Java regex); explore_code, who_calls, graph_symbol answer architecture questions.

05

Admin dashboard & RBAC

Web-based admin UI for managing agents, inspecting tasks, viewing guard violations, and monitoring server health. Role-based access control (admin, operator, auditor). Every admin action is audit-logged.

06

Ethical guardrails

Samvit's guard module scans every memory, message, and document for credentials, PII, and live data — configurable to redact, block, warn, or pass through. Every violation is logged and auditable in guard_violations.

For CTOs & core engineers

What Samvit actually implements — and why.

Every design decision is a tradeoff. This section shows the exact algorithm behind each primitive, what guarantees it provides, and what it deliberately does not guarantee. No hand-waving.

1 — Atomic task claiming: FOR UPDATE SKIP LOCKED

The hardest correctness requirement in a multi-agent task queue is preventing two agents from claiming the same task. Samvit solves it with a single CTE — no Redis, no distributed locks, no application-level retries. 

-- claim() — the full SQL that runs on every claim() call
WITH selected AS (
  SELECT id FROM tasks
  WHERE  status       = 'pending'
    AND  workspace_id  = $3          -- workspace isolation
    AND  tags && $3::text[]          -- OR tag filter (optional)
  ORDER BY priority DESC, created_at ASC
  LIMIT 1
  FOR UPDATE SKIP LOCKED            -- skip any row another txn holds
),
updated AS (
  UPDATE tasks
     SET status      = 'claimed',
         claimed_by  = $1,
         claimed_at  = now(),
         claim_token = $2           -- 256-bit random, checked on done()
    FROM selected
   WHERE tasks.id = selected.id
  RETURNING tasks.*
)
SELECT u.*, COALESCE(a.handle, 'unknown') AS created_by_handle
  FROM updated u
  LEFT JOIN agents a ON a.id = u.created_by;

What it guarantees

Exactly one agent wins per task, even under full concurrent load. PostgreSQL holds a row-level lock for the duration of the CTE — the losing agent sees zero rows (SKIP LOCKED skips the locked row entirely) and either claims the next task or gets null.

Crash recovery

Every claimed task has a claim_timeout (default 30 min) + 5 min grace period. The background cleanup loop (runs every 5 min) resets expired claims back to pending. An agent that crashes mid-task releases automatically — no human intervention.

What it does not guarantee

This is a polling model — agents call claim() on their own schedule. There is no push notification when a task becomes available. Recommended polling interval: 2–5 s. For long-lived work, call renew() to extend the lease.

2 — Dual-store memory: vector + KV in one call

remember(content, key?) always writes a vector embedding into semantic_memory. If key is set, it also upserts into kv_memory. recall() dispatches to the right store depending on which argument you pass. 

-- recall(query=...) → cosine similarity search
SELECT content, 1 - (embedding <=> $1) AS score
  FROM semantic_memory
 WHERE workspace_id = $2 AND namespace = $3
 ORDER BY embedding <=> $1   -- pgvector IVFFlat ANN index
 LIMIT $4;

-- recall(key=...) → O(1) exact key lookup
SELECT value FROM kv_memory
 WHERE workspace_id = $1
   AND namespace     = $2
   AND key           = $3;

Embedding model

BAAI/bge-small-en-v1.5 — 384-dim, runs locally via fastembed, no external API. Inference runs in the thread pool so it never blocks the async event loop. Content is truncated at 32 KB before embedding (512-token model max). NaN/Inf vectors are rejected before any DB write.

Namespace isolation

Every memory write defaults to the agent's private namespace (their handle). The global namespace is readable and writable by all agents in the same workspace. Attempting to write into another agent's namespace raises PermissionError at the tool layer — not a SQL constraint.

3 — Message delivery: join-table read tracking

Messages are stored once in messages. Each agent's read state is tracked in message_reads(message_id, agent_id) — a join table with a unique constraint. This gives exactly-once delivery per agent even under concurrent polls. 

-- read() — atomically marks messages as read and returns them
WITH marked AS (
  INSERT INTO message_reads (message_id, agent_id)
  SELECT id, $1 FROM messages
   WHERE workspace_id = $2
     AND (to_agent = $1 OR to_agent IS NULL) -- directed or broadcast
     AND NOT EXISTS (
       SELECT 1 FROM message_reads mr
        WHERE mr.message_id = messages.id AND mr.agent_id = $1
     )
  ON CONFLICT DO NOTHING         -- idempotent under concurrent polls
  RETURNING message_id
)
SELECT m.* FROM messages m
  JOIN marked ON marked.message_id = m.id
 ORDER BY m.created_at;

-- Peek without consuming: pass mark_read=false → skips the INSERT

Why not a read_by UUID[] array? Array updates require a full row lock and don't compose under concurrent writes — two agents reading simultaneously can race and lose one acknowledgment. The join table + ON CONFLICT DO NOTHING is lock-free and always correct.

4 — Ethical guard: regex + Shannon entropy

Every write (memory, message body, task title/description) passes through the guard before hitting the DB. Two layers run in sequence.

Layer 1 — Named patterns (60+ regexes)

JWT tokens, AWS/GCP/Azure keys, GitHub/GitLab tokens, Stripe/Twilio keys, private key PEM blocks, bcrypt/argon2 hashes, connection strings, credit card numbers (Luhn), SSNs, internal IPs, generic password = and secret = assignments. Each pattern carries a category (credential, pii, live_data) and severity.

Layer 2 — Shannon entropy

Strings of ≥ 20 characters from the Base64 alphabet are scored: $H = -\sum p_i \log_2 p_i$. If $H \geq 4.5$ bits/char and the string has ≥ 8 distinct characters, it's flagged as a high-entropy secret — catches API keys and tokens that don't match any named pattern. Prose and UUIDs are below the threshold by design.

-- Four modes (SAMVIT_GUARD_MODE env var)
redact  → replace match with [REDACTED:category] — default
block   → raise GuardError before any DB write — strictest
warn    → log violation, store as-is — for auditing without enforcement
off     → bypass entirely — for trusted internal pipelines

-- Snippets in the audit log: first 6 chars + "…" — never the full secret
-- Violations stored in guard_violations(agent_id, pattern_name, category, direction, tool)

5 — Code graph: AST (Python) + regex fallback (everything else)

index_code(path) walks the repo (up to 500 files, 512 KB/file), skips binaries via magic-byte detection, and builds a symbol graph in PostgreSQL. Querying is then instant for any agent — no re-reading of files.

Python: full AST

Uses ast.parse() — extracts modules, classes, functions, async functions, their parameters, decorators, docstrings, and call edges. Qualified names are computed via scope walking. Import statements are recorded as imports edges. Call sites are resolved to their qualified target where unambiguous.

JS / TS / Go / Rust / Java: regex

A language-specific regex parser extracts function declarations, class definitions, and import statements — no full parse tree. Enough to build the symbol index and call edges for who_calls and graph_symbol. Trade-off: no type information, no macro expansion, no template resolution.

-- explore_code("password validation") → vector search on docstrings + signatures
SELECT name, file_path, line_start, signature, docstring,
       1 - (embedding <=> $query_vec) AS score
  FROM code_nodes
 WHERE workspace_id = $1 AND repo_id = $2
 ORDER BY embedding <=> $query_vec LIMIT $3;

-- who_calls("hash_password") → reverse edge lookup
SELECT cn.name, cn.file_path, cn.line_start
  FROM code_edges ce
  JOIN code_nodes cn ON cn.qualified_name = ce.from_qualified
 WHERE ce.to_qualified ILIKE '%hash_password%'
   AND ce.edge_type = 'calls';

-- graph_symbol("AuthService", depth=2) → BFS via recursive CTE
WITH RECURSIVE bfs AS (
  SELECT ... FROM code_edges WHERE to_qualified = $symbol
  UNION
  SELECT ... FROM code_edges ce JOIN bfs b ON ... WHERE b.depth < $max_depth
)

6 — Auth: bcrypt + SHA-256 index, workspace-scoped queries

Token model

Tokens are samvit_-prefixed, 48-byte URL-safe random strings. On registration, the token is bcrypt-hashed (stored in token_hash) and its SHA-256 hex is indexed (stored in token_sha256). Every request does: SHA-256 lookup → O(log n) index scan → bcrypt verify → agent row. The SHA-256 index makes auth fast; bcrypt makes brute-force infeasible even with DB read access.

Workspace isolation

Every agent belongs to a workspace. Every table (tasks, semantic_memory, kv_memory, messages, code_nodes, code_edges) carries a workspace_id foreign key. The auth middleware sets the workspace on every request; every query appends WHERE workspace_id = $agent.workspace_id. Workspace cross-contamination requires a compromised token.

Questions

For CTOs, architects, and engineers.

How is this different from LangGraph / CrewAI?

Those frameworks define how agents execute (DAGs, loops, sub-agents). Samvit provides the shared state those agents read and write — memory, tasks, messages — across sessions and machines. They are complementary: LangGraph can use Samvit as its persistence layer.

Do developers need to install anything on their machines?

No. Samvit runs as a server. Developers only install an MCP client (Claude Code, Codex CLI) and point it at the Samvit server. All coordination happens server-side. Zero per-machine setup.

How do we secure Samvit in production?

Do not expose it to the public internet. Run behind a TLS-terminating reverse proxy (Caddy, nginx). Use strong SAMVIT_ADMIN_SECRET. Each agent gets its own bcrypt-hashed token. The ethical guard scans for credentials and PII. PostgreSQL is the single source of truth.

What infrastructure do I need?

One machine with Docker. PostgreSQL 16 (pgvector) for persistence. Minimum: 2 CPU cores, 4 GB RAM. No per-machine agents, no sidecars, no per-developer installs.

Does Samvit work with any AI client?

Any client that supports MCP connects — Claude Code, Codex CLI, Cursor, Kiro, OpenCode, Antigravity. Each agent gets its own bearer token. All share the same memory pool, task queue, message bus, and code index. samvit connect auto-configures all detected clients in one command.

What is on the roadmap?

Task dependencies, memory retention policies, workspace-scoped admin roles, agent capability registry, and Kubernetes Helm charts.
